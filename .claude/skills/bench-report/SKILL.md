# Benchmark report

Builds the report page for one benchmark-mode recording. The numbers, phases,
charts and table are generated by scripts; you write the words: the verdict,
the headline tiles and the findings.

The recording format is documented on the `Bench` class in
`packages/chat_rooms_with_livestream/lib/bench/bench.dart`, with a summary in
`lib/bench/README.md`. `examples/content.example.json` is the content of a
real report built this way (a Pixel 6a viewer smoke run). Use it as the
reference for tone and depth.

## Steps

1. **Analyze.** Write outputs to the scratchpad (or a temp dir), not the repo:

   ```bash
   python3 .claude/skills/bench-report/scripts/analyze.py "<recording>" -o <tmp>/analysis.json
   ```

   stdout is the full analysis minus the chart series. Read all of it. The
   series are in the file if you need to check a specific second.

2. **Check that the recording is usable.** Start with `warnings`: wrong build
   mode, device charging, no plateau, small peak load, call id mismatch,
   truncated lines. Then look at `call` (did the device join, and in which
   role?) and `durationS`. If the device never joined a call, say so and stop.
   There is nothing to report.

3. **Read the numbers, then decide what they say.** Go through the checklist
   below. Every claim you make must point at a value in the analysis (phase
   stats, `jankAttribution`, `stalls`, `logs`, `memory`, `thermal`,
   `timeToFirstFrame`).

4. **Write `content.json`** in the same temp dir, following the schema below.

5. **Render:**

   ```bash
   python3 .claude/skills/bench-report/scripts/render.py <tmp>/analysis.json <tmp>/content.json -o <tmp>/<name>.html
   ```

6. **Publish.** If the Artifact tool is available, publish the HTML as an
   artifact (icon `chart`, a one-sentence description) and give the user the
   link. Otherwise hand over the HTML file. In chat, give a short summary of
   the verdict and the main findings. The page holds the detail.

When a host and a viewer recording from the same run are both given, build
one report per file. Then compare them in each report's findings, or in an
`extraSections` entry. Line them up by `meta.ts` (UTC start of each
recording) plus `ms`.

## What to look for

- **Video quality under load.** Compare each loaded phase's `rtc` against the
  first `baseline` phase. Viewer: `sub.kbps`, `fps`, `lossPct`,
  `freezesTotal`, `jbMs`, `decMsPerFrame`. Host: `pub.kbps`, `fps`, `h`,
  `encMsPerFrame`, and `qualityLimitation`: `cpu` means the device couldn't
  keep up, `bandwidth` means the network couldn't.
- **UI thread.** Look at `jankPct`, `buildP90`, `rasterP90` and `lagP95` by
  phase. Build time high while raster time stays flat means Dart/widget work.
  Raster time high means the GPU or compositing.
- **Attribution.** `jankAttribution` compares jank in seconds with and without
  chat messages and with high and low call state updates, and gives
  correlations. Separate chat-driven cost from participant-driven cost. Point
  to the seconds that break the tie: a phase with one driver and not the
  other. Correlation with `load` alone is weak evidence, because load and
  chat often rise together.
- **Scaling.** `othersUsMax` is how long computing `otherParticipants` takes.
  Multiply it by call state updates per second: that is the per-update cost a
  selector on the participant list pays. This matters on the host, whose
  viewer count uses it.
- **Stalls.** List each entry in `stalls` with its time and what was
  happening then, such as a join, going live, or a ramp.
- **Resources.** CPU by phase. `memory` before, peak and after, and whether it
  returned to where it started. Thread count after leaving. `thermal` and
  battery, but only when the device wasn't charging.
- **Time to first frame.** Use `timeToFirstFrame.firstRtcWithVideoS -
  attachAtS` as an upper bound: stats arrive about every 2 s. Recordings made
  before the recorder fix have a `markSinceAttachMs` that is one report late.
- **Reconnects and logs.** `reconnects`: any is a finding. Group `logs` into
  benign teardown/negotiation noise and anything that points at a real
  problem.
- **What's missing.** A load that never plateaued, no chat traffic, a single
  device, or a short run each limit what the report can claim. Say which.

## content.json

```json
{
  "title": "Pixel 6a Viewer Run",
  "eyebrow": "Livestream benchmark · viewer side · 10k run",
  "h1": "Pixel 6a viewer run",
  "lede": "Two or three sentences: is the recording valid, what load it saw, the one-line verdict.",
  "tiles": [
    {"status": "good|warn|bad|info", "pill": "Unaffected", "value": "720×960 · 30 fps", "label": "What the number means, one line"}
  ],
  "timelineIntro": "optional - replaces the default text above the chart",
  "phaseNames": {"0": "optional - rename phase rows by index"},
  "focus": 76,
  "findings": [
    {"tag": "Video", "title": "Short claim", "paragraphs": ["Evidence, with numbers."], "bullets": ["optional"]}
  ],
  "extraSections": [{"title": "Host vs viewer", "html": "<p>optional</p>"}],
  "nextTitle": "Before the next run",
  "next": ["<b>Concrete action.</b> Why, tied to this recording."]
}
```

- `title`: two to four words naming the run (device + role, or run name), with
  no explanation after a dash or colon.
- `tiles`: four is right. Pick the headline numbers: video quality, time to
  first frame, the worst UI regression, and CPU or memory. `status` colors the
  pill: `good` unchanged under load, `warn` degraded, `bad` broken or unusable.
- `findings`: order them by importance. Each title is a claim ("Jank follows
  the chat messages"), not a topic ("Jank"). Give numbers, and the seconds or
  phase they come from. Don't repeat the phase table.
- `focus`: which second the chart readouts show when the page opens. Leave it
  out to use the phase with the worst jank.
- Strings may contain inline HTML (`<b>`, `<code>`). Don't add styles.

## Writing

Write for the team deciding whether the SDK holds up at this scale. Use plain,
direct sentences, and give the number before the adjective. Separate what the
data shows from what you infer, and give the reason for each inference ("the
likely cause is … because …"). Don't add a finding just to fill the page: if
nothing changed under load, that is the finding.
